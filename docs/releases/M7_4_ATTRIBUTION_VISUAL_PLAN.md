# M7.4 Attribution - Interactive Visualization & Delivery Plan

> **Audience**: Engineering and product design
> **Status**: Ready for implementation planning; no production code in this document
> **Baseline**: origin/main at aef0c96 (2026-08-07 review)
> **Milestone**: M7.4 Explainability, after M7.1 Activity, M7.2 Watchtower, and M7.3 Scenario

## 1. Decision We Are Building

M7.4 must answer one precise, auditable question:

> Given two complete, replayable scenario inputs, **why did the all-project return rate change?**

The first release therefore compares two M7.3 Scenario input sets and attributes the change in Core
result.return_rate to changed input fields. It is not a generic charting feature, a second calculator,
or a claim about the historical result that was displayed by an older Core version.

### First-release product decision

| Item | M7.4 v0.1 decision |
|---|---|
| Comparison source | Two complete Scenario.engine inputs from the same local case |
| Target | return_rate only, labelled **全案投報率** |
| Computation | Replay both inputs with the currently loaded Core in the Pyodide Worker |
| Exact method | Shapley for at most 10 approved changed features |
| Fallback | OAT (one-at-a-time), always with an explicit interaction residual |
| Persistence | None. Attribution is an ephemeral Core output, not Activity, History, Decision, or Scenario data |
| Initial supported changes | Scalar leaves under engine.params, including scalar params.財務覆寫.* leaves |

return_rate must never be labelled "IRR". They are different indicators. The display unit is
**percentage points (ppt)**: a raw delta of -0.021 is shown as -2.10 ppt, not -2.10%.

## 2. Non-Negotiable Boundaries

1. **No existing Core formula is edited or copied.** attribution.py only composes calls to the existing
   recompute(engine) entry point and reads its result.
2. **The UI calculates nothing.** It sends the two complete inputs and target to core-runtime.worker.js;
   all delta, feature impacts, residuals, method selection, hash, rounding, and conservation flags return
   from Core.
3. **No mutation of M7.3 data.** Existing scenario.schema.v0.1.json, activity, workflow, and project
   schemas remain byte-for-byte frozen.
4. **No inferred output is written back to CaseStore.** The browser may keep a memory-only cache keyed by
   input hashes for the open page, but it may not store attribution in IndexedDB, Activity, snapshots, or
   an export bundle.
5. **No PII and no real cases enter version control.** Fixtures use synthetic scenario IDs and inputs.
6. **No false precision.** A result generated by replaying old inputs on today's Core is explicitly labelled
   "以 Core {version} 重播"; it is not presented as the number seen on the original date.

## 3. Comparison Contract

### 3.1 Replayable candidate rule

The picker accepts only a candidate with a complete engine object. In M7.4 v0.1 that means M7.3
scenarios. Existing History snapshots that contain only input_hash remain visible in the case timeline,
but cannot be selected for attribution until they carry a full engine input set.

This is deliberate: a hash proves provenance but cannot be replayed by itself.

### 3.2 Input difference rule

Core creates a deep diff between before and after, then admits only scalar paths in:

~~~text
engine.params.*
engine.params.財務覆寫.*
~~~

It rejects a comparison containing a changed floors, owners, case_type, mode, array shape, or an
unrecognised structural path. It does not merge those changes into an opaque "other" contribution. A
causal explanation that silently lumps unknown changes together is less useful than a clear refusal.

The feature identifier is the canonical path, for example params.住宅單價. The label is taken by Core
from that path, never invented by the UI. Future releases may add approved feature groups for floors and
owners after a separate contract and test suite.

### 3.3 Core public API

~~~python
attribute(before: dict, after: dict,
          target: str = "return_rate", method: str = "auto") -> dict
~~~

before and after are complete engine inputs. target="return_rate" is the only supported v0.1
target. method="auto" resolves to shapley when the approved changed-feature count is at most 10;
otherwise it resolves to oat.

Implementation rules:

- Canonicalise and hash both inputs with the existing input_hash().
- Recompute the two endpoint results with the same loaded Core.
- Extract result.return_rate inside Core, not in JavaScript.
- For exact Shapley, evaluate every subset of the changed features. At 10 features this is at most
  2^10 = 1024 recomputations.
- For OAT, apply each changed feature independently to the baseline and set
  residual = delta - sum(contributions). This residual represents interaction left unexplained by OAT;
  it is never silently dropped.
- Do not mutate either input object while constructing counterfactual inputs.

For Shapley, the raw residual should be zero within a documented tolerance (1e-9), except for floating
point noise. The field remains present in every response so downstream presentation has one stable
contract.

### 3.4 Versioned output schema

Create an additive, frozen output contract:

~~~text
schemas/attribution.schema.v0.1.json
schema_version: "attribution-0.1"
~~~

Suggested shape (field names are normative; exact JSON Schema constraints are an engineering task):

~~~json
{
  "schema_version": "attribution-0.1",
  "status": "ok",
  "core_version": "0.5.0",
  "target": {
    "id": "return_rate",
    "label": "全案投報率",
    "raw_unit": "ratio",
    "display_unit": "percentage_points",
    "higher_is_better": true
  },
  "before": { "input_hash": "sha256:...", "value": 0.0852 },
  "after": { "input_hash": "sha256:...", "value": 0.0642 },
  "delta": -0.021,
  "contributions": [
    {
      "feature_id": "params.住宅單價",
      "label": "住宅單價",
      "before_value": 92,
      "after_value": 88,
      "impact": -0.018
    }
  ],
  "residual": { "impact": 0.0, "kind": "numeric" },
  "method": {
    "requested": "auto",
    "resolved": "shapley",
    "feature_count": 1,
    "runs": 2,
    "exact": true
  },
  "conservation": { "tolerance": 1e-9, "raw_ok": true },
  "presentation": {
    "precision": 2,
    "before": 8.52,
    "after": 6.42,
    "delta": -2.10,
    "contributions": [
      { "feature_id": "params.住宅單價", "impact": -1.80 }
    ],
    "residual": 0.00,
    "rounding_reconciliation": 0.00,
    "display_ok": true
  }
}
~~~

presentation is intentionally generated by Core. Independent browser rounding can make visibly rounded
rows fail to sum to the visibly rounded delta. If it is needed, Core emits a separate
rounding_reconciliation row; it must not relabel display rounding as an economic interaction residual.

### 3.5 Version governance

| Change | Required action |
|---|---|
| New Attribution result contract | Add attribution.schema.v0.1.json; never modify frozen schemas |
| Schema registration | Add its SHA-256 to tools/check_schema_freeze.py; mirror it in governance/VERSION_POLICY.md |
| Core capability | Bump CORE_VERSION from 0.4.0 to 0.5.0; add CHANGELOG entry. Existing project results are not rewritten |
| Browser Core | Regenerate apps/web/core-bundle.js from the Core source and pass Gate 9 |
| UI source map | Add Attribution rows to docs/architecture/UI_BINDING_MAP.md, binding every shown number to the Attribution output contract |

No project-schema migration is required because attribution is neither stored in Project JSON nor a new
project field. The new output schema itself is versioned and frozen from its first release.

## 4. Interaction and Visual Design Handoff

### 4.1 Where it lives

Place the surface in apps/web/workspace.html, adjacent to the existing Scenario and case-history work.
It is a work panel called **歸因比較**, not a dashboard hero and not a new top-level product. This keeps the
mental flow intact:

~~~text
Scenario chooses two complete inputs -> Attribution explains the change -> PM records a separate decision if needed
~~~

The attribution result never creates a Decision Record automatically. An explanation may inform a decision;
it is not the decision itself.

The bridge is a **conservation view**, not a time series. Contributions are ordered by absolute impact
for reading, and the caption must state that Shapley is order-independent. Do not use arrows, timeline
labels, or animation that implies "residential price changed first".

### 4.3 Mobile / narrow layout

At below 768 px, selectors stack vertically, the summary remains visible first, and the bridge changes to
a vertical list with fixed-width numeric columns. The two endpoint values and the conservation line must
remain on screen. Do not make the data available only through horizontal scrolling or hover.


### 4.4 Required interactions

| Interaction | Expected behaviour | Data authority |
|---|---|---|
| Choose baseline / comparison | Only complete, selectable scenario inputs appear. The same source cannot occupy both selectors | CaseStore metadata only |
| Press 計算歸因 | Sends complete engines, target, and auto to the Worker. It does not calculate in the page | Core Worker |
| Change a selector after a result | Marks the result stale and hides prior numbers until the user runs again | UI state only |
| Hover / keyboard focus a bridge row | Highlights the matching row in the changed-field table and exposes before/after values | Core response |
| Select a changed-field row | Opens an inline detail area: canonical path, values, impact, method, and provenance hashes | Core response |
| Open method information | Explains Shapley exact vs OAT and what residual means. It must not claim a causal finding beyond the selected inputs | Static explanatory copy |

No drag-to-change input, chart editing, manual contribution override, or automatic run on every selector
change belongs in M7.4. Exact Shapley can run 1,024 Core replays; a deliberate button and visible progress
are more honest and more controllable.

### 4.5 States design must deliver

| State | User-visible content | Designer instruction |
|---|---|---|
| Ready | Two selectors and one clear compute action | Avoid an empty decorative chart |
| Computing | Core 正在執行反事實重算 and an indeterminate progress bar | Keep prior controls fixed; disable repeat request. Show the exact run count only after Core returns it |
| Shapley exact | Exact badge, bridge, changed-field table, raw conservation pass | Do not use colour as the only signal |
| OAT approximation | OAT 近似 badge and a visually explicit residual row | Residual gets equal visual weight; never hide it below the fold |
| No changed supported input | 兩個方案沒有可歸因的 params 差異 | Show source hashes and tell the user why no chart exists |
| Unsupported structural change | Name paths such as owners or floors; state that this comparison is out of M7.4 v0.1 scope | No fabricated other bar |
| Core unavailable / error | Existing Core unavailable fallback plus retry action | Do not fall back to JS computation |

### 4.6 Visual language and accessibility

- Use a restrained operational layout consistent with the Workspace: compact section heading, data-dense
  rows, an 8 px-or-less radius only where existing components use it.
- Positive and negative impacts use the existing semantic colour tokens, plus a sign (+ / -) and text.
  For a future lower-is-better target, the target metadata controls interpretation; colour alone may not
  decide "good" or "bad".
- All numeric columns use tabular numerals, a fixed right-aligned width, and non-wrapping units. Labels may
  wrap without changing value-column alignment.
- The conservation status includes both an icon/text token and the exact displayed equation.
- Tooltips must be keyboard reachable. Hover is enhancement, never the sole route to values or meaning.

## 5. Engineering Delivery Plan

### Slice A - Core contract and exact algorithm

**Files**: new core/redcf/attribution.py, new schemas/attribution.schema.v0.1.json,
core/redcf/__init__.py, core/redcf/_version.py, CHANGELOG.md, freeze/version-governance files.

1. Implement a pure attribute() module around recompute() and input_hash().
2. Implement the approved scalar diff and structured unsupported-path errors.
3. Add exact Shapley and OAT fallback, raw conservation validation, and Core-owned presentation rounding.
4. Validate every successful report against the new schema before it leaves Core.
5. Export attribute from core.redcf; update Core version to 0.5.0.

**Done when**: Python tests prove exact conservation, order independence, no input mutation, and the schema
freeze gate includes the new file without changing an old one.

### Slice B - Browser Core transport

**Files**: apps/web/core-runtime.worker.js, apps/web/core-runtime.js, generated
apps/web/core-bundle.js, tools/build_core_bundle.py only if runtime-data inclusion needs expansion.

1. Add an attribute Worker message that invokes _redcf.attribute(...) and returns its JSON unchanged.
2. Expose a stable loading lifecycle only; the current synchronous Pyodide call must not pretend it can stream
   subset-level progress. Core returns the authoritative run count in the final report.
3. Add runtime.attribute(before, after, target, method) to the main-thread wrapper.
4. Rebuild the Core bundle and pass tools/check_core_bundle.py.

**Done when**: the browser runtime reports the same report as Python for a fixed synthetic pair, and a worker
error reaches the UI as an explicit error rather than an empty chart.

### Slice C - Workspace interaction surface

**Files**: apps/web/workspace.html and the smallest existing Workspace helper module, if one is already
used. Do not add a new framework.

1. Add the 歸因比較 panel and source selectors populated from M7.3 scenarios.
2. Keep source labels and stale/loading state in UI memory only.
3. Render the summary, bridge, table, detail disclosure, progress, and all required error states strictly
   from the Core response.
4. Register every visible numeric field in UI_BINDING_MAP.md.

**Done when**: the UI contains no delta formula, no threshold decision, no residual computation, and no
write path to CaseStore/Activity for attribution.

### Slice D - Verification and release hygiene

**Files**: new Python and web tests, docs, version metadata, generated bundle.

1. Run all existing Python, schema-freeze, Core-bundle, web headless, PII, and image-whitelist gates.
2. Test a clean browser session and a browser with existing M7 activity data; attribution must be read-only
   in both.
3. Verify the dense desktop and narrow mobile states manually with the synthetic fixture.
4. Update docs/architecture/M7_CASE_OS_SPEC.md status and the M7.4 Definition of Done only after all gates
   are green.

## 6. Test Strategy and Acceptance Matrix

### Core tests (tests/test_attribution.py)

| Test | Assertion |
|---|---|
| A. Exact conservation | sum(raw impacts) + residual == delta within 1e-9 |
| B. Shapley order independence | Same changed set presented in different key orders produces the same contribution per feature |
| C. One change | Single feature impact equals delta; residual is zero within tolerance |
| D. OAT interaction | More than 10 approved changes resolves to OAT and exposes a non-hidden residual when interactions exist |
| E. Endpoint replay | before.value, after.value, and hashes equal direct Core replays |
| F. Unsupported diff | Changed floors, owners, mode, or list shape returns a structured refusal, not an other bar |
| G. Target guard | Unknown target and an unavailable result field fail explicitly |
| H. Input immutability | Calling attribution leaves deep copies of both input engines unchanged |
| I. Schema / display contract | Every successful report validates against attribution-0.1; Core's displayed equation conserves too |

### Web and worker tests

Create tests/web/test_attribution_wiring.mjs.

- Mock the Worker response and assert that workspace.html renders returned values verbatim.
- Assert a selector change invalidates rather than reuses a previous report.
- Assert the request contains full before / after engines and never a UI-derived delta or contribution.
- Assert unsupported/error/OAT/zero-change states have visible explanatory text.
- Assert no attribution result is passed to CaseStore.putCase, addActivity, or scenario persistence.
- Assert Core bundle synchronization after adding attribution.py.

### Regression gates that must remain green

## 7. Release Criteria

M7.4 is ready only when all of the following are true:

- Two M7.3 scenarios can be selected and replayed using the same loaded Core.
- The product labels the target as **全案投報率**, with percentage-point deltas.
- Every displayed impact and residual is a Core field with a documented schema source.
- Exact Shapley is order-independent and conserves to the documented tolerance.
- OAT states are visibly labelled approximate and show their residual.
- Unsupported structural changes refuse clearly instead of producing a misleading chart.
- Attribution never changes a scenario, snapshot, Activity event, or Decision Record.
- New output schema is versioned, frozen, and registered; old schemas remain unchanged.
- Browser bundle and all existing gates pass.

## 8. Explicitly Deferred

- Comparing History snapshots without complete engine inputs.
- Floor, owner, and allocation-level feature grouping.
- Targets other than return_rate (for example shared cost ratio or owner return value).
- Persisting, exporting, printing, or automatically logging attribution reports.
- M7.5 volume/floor/GIS visualization.
- Recommendations such as "therefore negotiate price first". That remains the Strategy layer's job.

This scope is intentionally narrow. It ships a defensible explanation surface first: one target, two complete
inputs, one authoritative Core path, and a visible conservation equation.
