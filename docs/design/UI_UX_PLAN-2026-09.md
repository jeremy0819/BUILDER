## 2. 四步動線・資訊架構

### 2.1 根因

四步動線是**後來嫁接**的骨幹，「一個工具一頁」的舊結構沒退場，於是兩套案件管理平行存在：

| | `dashboard.html`（四步內） | `workspace.html`（四步外） |
|---|---|---|
| 專屬功能 | 產權清冊、逐層樓板、量體生成、現金流、傳動軸 | 同意看板、任務、決策日誌、時間軸、wf 匯出 |

使用者要記住「同意看板在那邊、產權清冊在這邊」。**複雜度來自結構重疊，不是版面。**

### 2.2 收斂原則

> **每一步只回答一個問題，答完才進下一步。**
> 判斷某個區塊該放哪一步，就問「它幫使用者回答的是哪一個問題」——
> 回答不了就不屬於主動線，收進摺疊或案件櫃。

### 2.3 目標架構

| 步驟 | 問題 | 內容 | 異動 |
|---|---|---|---|
| **① 基地** | 這塊地能蓋多少？ | 基地條件輸入・逐層樓板／量體生成・容積查核結果 | **移出** 地政資訊區（新案全空卻佔滿版）→ 收為摺疊 |
| **② 產品** | 蓋出來值不值得？ | 四項 Core 權威數字・傳動軸滑桿・健檢與敏感度 | **移入** 傳動軸滑桿自 ①——這一步才是「調產品」 |
| **③ 人心** | 誰會點頭？先談誰？ | 戶別盤面（作用中案件）・整合推演沙盤 | **移入** 同意看板、任務（自 workspace）——人的事歸人心 |
| **④ 決策** | 下一步該做什麼？ | 四象限判讀圖・逐型對策與行動順序 | **移入** 決策日誌、時間軸（自 workspace） |

### 2.4 兩項結構調整

**workspace.html 降級為「案件櫃」**
五項功能拆散歸位後，它只留**選案**與**匯出入**。不再是與四步平行的第二套案件管理。

**建案入口 5 → 1**
目前 5 個頁面都能建案。只有起始頁真正建案，其餘改為跳轉。
功能一項不減，要記的概念從 5 個變 1 個。

## 3. 來源語意系統

這個產品最特別的紀律是「每個數字都要說出自己從哪來」。
視覺系統的核心不是配色，是**讓來源看得見**——只有三種，沒有第四種。

| 標籤 | 意義 | 紀律 | 顏色 |
|---|---|---|---|
| `CORE` | 由 `core/redcf` 算出的權威數字（允建容積、銷售坪數、共同負擔比、全案投報率） | 介面一律**逐欄搬運，不得換算** | `#5a48d6` |
| `INPUT` | 使用者登打的**事實**（基地面積、容積率、戶數）——抄謄本抄來的，不是算出來的 | 計算核心不可用時**仍可記錄**，因為它本來就不需要計算 | `#68707d` |
| `DECISION` | 決策引擎輸出（GO／CAUTION／STOP、完工機率、破局引爆點） | **存活率尚未校準**，凡顯示此類數值處一律附標示 | `#a86616` |

### 3.1 既有 Token（沿用，不新增）

| Token | 淺色 | 深色 |
|---|---|---|
| `--uros-accent` | `#5a48d6` | `#9b8cff` |
| `--uros-ok` | `#16845b` | `#54c99a` |
| `--uros-warn` | `#a86616` | `#e2a44e` |
| `--uros-err` | `#c33f54` | `#ef7889` |
| `--uros-mute` | `#68707d` | `#9aa2af` |
| `--uros-line` | `#dfe3e8` | `#2b303b` |
| `--uros-ink` | `#16181d` | `#eef0f5` |
| `--uros-panel` | `#ffffff` | `#171a21` |

### 3.2 視覺語言收斂

目前走一輪會遇到三種：起始頁深色終端風 → ①②④ 淺色 → ③ 進場深色遊戲風。

**建議**：保留起始頁深色（它像開機畫面，說得通）；
**收斂 ③ 的進場黑畫面**——按下「開始整合」後本來就變淺色，那一下的全黑沒有作用。

## 4. 狀態矩陣

> 每一格都要有明文規定的長相。**沒有規定的格子就會被即興發揮**，
> 而即興發揮出來的通常是「顯示一個看起來合理的數字」——那正是這個產品最不能犯的錯。

### 軸一・計算核心

| 狀態 | 顯示 | 紀律 |
|---|---|---|
| 就緒 | `179.9%` | 數值＋來源標籤 |
| 啟動中 | `計算中…` | 明示還在跑，**不得先給估算值** |
| 連不上 | `取不到` | **不可再顯示「計算中」**——它不會再算了 |

### 軸二・決策綁定（N1 二元組）

| 狀態 | 顯示 | 說明 |
|---|---|---|
| 綁定成立 | `CAUTION` | `input_hash` 與 `core_version` 皆相符 |
| 尚未產生 | `—` | 標「尚未產生判定」 |
| 跨版本 | `—` | 標「判定由其他 Core 版本算出，需重算」 |
| 輸入已變 | `—` | 標「輸入已變更，需重算」 |

### 軸三・快照陳舊（與綁定是**兩件事**）

0.4.0 的判定配 0.4.0 的快照，**是一致的歷史配對，綁得上**。
但現行 Core 是 0.6.0——數字沒錯，公式已經換過。

- 陳舊時在導覽列說明列常駐標示：`⚠ 數字來自 Core 0.4.0 快照（現行 0.6.0）`
- **不隱藏數值**，因為它仍是當時的事實

### 貫穿全矩陣・未校準標示

`stage_tree.json` 自述「p_survival 仍為示意預設，尚未經真實成敗案校準」，
而它正是 GO／CAUTION／STOP 的來源。

- 凡顯示 verdict、完工機率、EV 之處**一律附標示**
- 文字取自 Core 的 `_note`，**不由各頁自己寫一份**
- ⚠️ **目前 ④ 的四象限圖與導覽列都沒有這個標示**（① 的案件卡有）

## 5. 元件規格

數值取自 `os-unified.css` 既有實作，不是新發明的尺寸。

### 5.1 數值格（KPI Cell）

```
padding 13px 14px ｜ radius 8px ｜ border 1px #dfe3e8
標籤   10.5px / #68707d
數值   750 19px/1.2 mono / #16181d
來源   9.5px mono — CORE #5a48d6 ／ INPUT #68707d ／ DECISION #a86616
```

- **取不到**：數值改 13px/400 `#68707d`，內容「—」或「取不到」，**不得填 0**
- **千分位**一律加；單位與數值同列、11px `#68707d`

### 5.2 空狀態

**三段式**：發生什麼事 → 為什麼 → 下一步能做什麼（**必含可按的動作**）

- **禁止**只有一句「尚無資料」而沒有出路——② 的預設分頁曾整片空白，讀起來就是壞頁
- 按鈕：height 32px、radius 6px、padding 0 14px、11.5px（沿用 `.uros-view-tabs` 尺寸）
- 語氣用使用者的話，不是系統的話（「還沒有案件」不是「無資料」）

### 5.3 警語條

| 類型 | 左邊界 | 用途 |
|---|---|---|
| 模型限制 | 2px `#a86616` | 存活率未校準・非投資結論 |
| 系統失效 | 2px `#c33f54` | 連不上計算核心 |

- **絕不**把原始例外丟給使用者。技術細節收進 `title`／診斷紀錄
- **位置紀律**：警語要放在「使用者會看到那個數字的地方」——
  放在規劃疊層裡，按下開始整合疊層就收掉了，盤面上看不到，等於沒有
- 語氣講原因與下一步，不講錯誤代碼

### 5.4 四步導覽列

每步顯示**一個有資訊量的數字**——③ 顯示「18/42 同意」而不是「42 戶」（後者不會變，看了等於沒看）。

**目前的缺口**：導覽列說 `CAUTION`、頁面本體說「待判讀」，同畫面兩個答案。

- **成因**：導覽列讀**已存的** decision，④ 的面板只認**本次即時跑**的結果——
  兩個表面回答不同問題卻沒區分
- **修法**：導覽列標「快照判定」，面板標「本次分析」，**兩者並存不互相取代**

## 6. 手機規範（390 × 844）

### 6.1 實測問題

| 項目 | 值 |
|---|---|
| ① 基地頁小於 12px 的文字 | **149 處** |
| 觸控目標小於 44px | **18 個** |
| 導覽列固定佔用 | 68 px（844px 螢幕的 8%） |
| 整頁橫向溢出 | 0 ✓ |

### 6.2 規範

- **字級下限 12px**：供閱讀的文字不得低於 12px。
  單位、來源標籤等附屬字可到 10.5px，但**不得承載使用者必須讀懂的資訊**
- **觸控目標 44 × 44**：所有可按元素。
  目前 32px 高的分頁鈕在手機要加大到 44px（桌機維持 32px，用 media query 分開）
- **導覽列可收合**：向下捲動時收成單列 36px，只留當前步與數字
- **輸入框高度 44px**（原 padding 7px 9px 約 36px）；說明文字 11px，不再壓到 10.5px

### 6.3 設計前提

> **手機不是縮小的桌機。**
> 在工地、在說明會現場、在地主家客廳打開的就是手機——
> 這三個場景要能**單手看數字**，不需要看得到全部四步。
